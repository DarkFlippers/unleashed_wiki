# MIFARE Ultralight AES (MF0AES20)

**MIFARE Ultralight AES** — це Ultralight із взаємною автентифікацією **AES-128** замість пароля (NTAG21x) чи
3DES (Ultralight C). Він має 60 сторінок, три односпрямовані лічильники, 48-байтовий ECC-підпис оригінальності,
необов'язковий режим **Random ID** і необов'язкове **secure messaging** (кожна команда й відповідь захищені
CMAC).

::: tip Unleashed
Підтримка Ultralight AES (зчитування, словникова атака, введення ключа вручну, емуляція, зворотний запис,
декодування конфігурації, Random ID, secure messaging) — можливість Unleashed, перевірена на справжній картці
MF0AES20 за еталонними даними з Proxmark3.
:::

## Що з ним робить Flipper

| Можливість | Подробиці |
|---|---|
| Визначення та зчитування | Визначається як `Mifare Ultralight AES`, ATQA `0044`, SAK `00`, `60/60` сторінок на відкритій картці, лічильники. |
| Підпис оригінальності | Зберігається у файлі `.nfc` рядком `AES signature:` (48 байтів) і відтворюється під час емуляції, тому перевірка підпису у зчитувача проходить. |
| Автентифікація AES | Трикрокове «запитання-відповідь» AES, після чого читаються захищені сторінки. |
| Словникова атака | Запускається автоматично при неповному зчитуванні: **MFUL AES User Dictionary**, потім **MFUL AES System Dictionary**. |
| Ключ вручну | `Saved → <картка> → Unlock` → **«Enter key in hex»** (16 байтів) → підтвердити **Unlock**. |
| Керування ключами | `NFC → Extra Actions → MIFARE UL AES Keys` → **Add** / **List**. |
| Зворотний запис | **Write (Keep Key)** / **Write (Copy Key)** для повністю зчитаного дампа. |
| Емуляція | Повна, включно з автентифікацією AES з боку картки, бар'єром AUTH0 і secure messaging. |
| Декодування конфігурації | `Info` показує блок **UL-AES Config** (див. нижче). |
| Random ID | Визначається й показується (`Random ID: on`); **Reveal Real UID** намагається відновити справжній UID. |

Словники: системний `/ext/nfc/assets/mf_ultralight_aes_dict.nfc` (заводський нульовий ключ, повторно використаний
як AES `BREAKMEIFYOUCAN!` та інші поширені типові ключі з Proxmark3), користувацький
`/ext/nfc/assets/mf_ultralight_aes_dict_user.nfc`. Заводська картка використовує нульовий ключ
`00000000000000000000000000000000` і для DataProtKey, і для UIDRetrKey.

## Зчитування захищеної картки

1. `Main Menu → NFC → Read`, піднесіть картку.
2. Відкриті сторінки зчитуються; якщо на картці є область, захищена AES, словникова атака запускається сама
   (спочатку користувацький словник, потім системний).
3. Якщо ключ підходить, усі сторінки зчитуються, а ключ показується й зберігається разом із дампом. Якщо ні, ви
   отримаєте часткове зчитування (наприклад, `42/60` сторінок) і **«AES-protected pages!»** — без зависання й без
   витрачання спроб на картці з необмеженою кількістю спроб.
4. Збережіть картку. Пізніше можна повторити спробу через **Unlock with Dictionary** (додавши ключі) або
   **Unlock** (ключ вручну).

::: warning Порядок байтів ключа
Прямий запис сторінок (наприклад, `hf mfu wrbl` у Proxmark3) зберігає ключ у **порядку пам'яті мітки**; рушій AES,
ручне введення у Flipper і `hf mfu aesauth --key` у PM3 використовують **зворотний** порядок. Картка, у якої
сторінки `0x30–0x33` читаються як `A0A1A2A3 A4A5A6A7 A8A9AAAB ACADAEAF`, автентифікується ключем
`AFAEADACABAAA9A8A7A6A5A4A3A2A1A0`. Вручну відновлений ключ вводьте **в порядку AES**. У збереженому `.nfc`
сторінки ключа (`Page 48`–`51`) зберігаються в порядку пам'яті мітки, щоб їх можна було записати назад без змін;
рядок `DataProtKey:` на екрані — лише спосіб відображення.
:::

## Пам'ять і конфігурація

| Елемент | Розташування |
|---|---|
| DataProtKey | сторінки `0x30`–`0x33` |
| UIDRetrKey | сторінки `0x34`–`0x37` |
| CFG | сторінка `0x29`: байт 0, біт 0 = `RID_ACT`, біт 1 = `SEC_MSG_ACT`; байт 3 = `AUTH0` |
| ACCESS | сторінка `0x2A`: байт 0, біт 2 = `CNT_RD_EN`, біт 3 = `CNT_INC_EN`, біт 6 = `CFGLCK`, біт 7 = `PROT`; байти 2–3 = `AUTH_LIM` |
| LOCK_KEYS | сторінка `0x2D`: байт 0 = біти блокування окремих ключів |

Блок **UL-AES Config** в `Info` розшифровує ці значення, наприклад:

- `Auth from: off (open)` або `Auth from: page 0x10 (r+w)` / `(write)`: `AUTH0` і `PROT`;
- `Auth limit: unlimited` або `Auth limit: N (locks!)`;
- `Counter 2: rd open / inc auth` і подібне;
- `Random ID: on/off`, `Secure msg: on/off`, `User cfg: open/locked`, `Key lock: DP N / UID N`;
- `Real UID:` після розкриття справжнього UID.

::: danger Не експериментуйте з цими бітами
`CFGLCK` блокує конфігурацію **назавжди**, `AUTH_LIM` вмикає блокування після невдалих автентифікацій, а
`LOCK_KEYS` і статичні байти блокування можуть «окирпичити» картку. Ніколи не змінюйте їх на картці, яка вам
потрібна. Зауважте також, що `hf mfu info` у PM3 підписує сторінки `0x34`–`0x37` у MF0AES20 за застарілим
шаблоном Ultralight (`cfg0/cfg1/PWD/PACK`); довіряйте таблиці вище.
:::

## Зворотний запис дампа

Пропонується лише для **повністю зчитаного** дампа Ultralight AES, двома пунктами:

- **Write (Keep Key)**: записує сторінки даних `0x04`–`0x27`; ключ цільової картки залишається.
- **Write (Copy Key)**: сторінки даних плюс **DataProtKey** (`0x30`–`0x33`) із дампа.

Правила, вбудовані у прошивку:

- Запис **спочатку автентифікується до цільової картки** словниковим ключем, тому *поточний* ключ цілі мусить
  бути у словнику (заводський нульовий ключ там є).
- Конфігураційні сторінки й сторінки блокування `0x28`–`0x2F` **ніколи** не записуються; UIDRetrKey
  (`0x34`–`0x37`) не записується ніколи.
- Ціль мусить бути того самого **типу**; UID збігатися не мусить.

## Емуляція

`Saved → <картка> → Emulate`. Емульована картка відповідає на GET_VERSION, віддає підпис, лічильники й
конфігурацію так само, як справжня, виконує автентифікацію AES з боку картки, використовуючи
`reverse(сторінки 0x30–0x33)` як ключ, відкидає хибні ключі й дотримується `AUTH0`. Зауважте: обмежені читання
без автентифікації повертають «загорнуті» дані ранніх сторінок, а не NAK.

## Random ID

Коли встановлено `RID_ACT`, картка під час кожного вибору показує **випадковий 4-байтовий UID, що починається з
`08`**; справжній 7-байтовий UID прихований до автентифікованого читання. Flipper показує випадковий UID і
`Random ID: on`. Для таких карток у меню є **Reveal Real UID**: він підтверджує дію попередженням, перечитує
картку й намагається автентифікуватися (типовий нульовий UIDRetrKey), щоб розкрити статичний UID, який далі
показується як `Real UID:` у поданні конфігурації.

## Secure messaging (CMAC)

Коли встановлено `SEC_MSG_ACT`, після автентифікації **кожна** команда й відповідь мусять нести CMAC. Flipper
обробляє це адаптивно: після автентифікації перше звичайне `READ`/`WRITE` не вдається (справжній чип просто
замовкає, що зчитувач бачить як тайм-аут), прошивка автентифікується повторно й перемикається на `READ`,
`READ_CNT` і `WRITE`, обгорнуті MAC. Лічильник команд зростає на 2 за обмін (команда використовує `CmdCtr`,
відповідь — `CmdCtr+1`). Перевірено на обладнанні: повне зчитування 60/60 через CMAC без розбіжностей MAC,
лічильники через CMAC, сторінки ключів `0x30`–`0x37`, замасковані нулями в дампі, і зворотний запис сторінок
даних через CMAC.

Емулятор також володіє secure messaging: він перевіряє MAC команди, обгортає MAC кожну відповідь, замінює ACK на
`WRITE` на MAC і скидає сесію в разі хибного MAC.

::: warning Чи можна це повернути
Коли `SEC_MSG_ACT` увімкнено, запис конфігурації у захищеній області потребує запису з автентифікацією CMAC, чого
Proxmark3 робити не вміє, а Write у Flipper пропускає (конфігураційні сторінки не записуються ніколи). Не
встановлюйте `AUTH0 ≤ 0x29` на картці з secure messaging, бо потім можете не зуміти вимкнути цей режим.
:::

### Відлагоджувальні маркери

З `Settings → System → Log Level → Debug` можна відслідкувати в логах, що відбувається, — наприклад,
`UL-AES: plain read failed post-auth, switching to secure messaging`,
`UL-AES response MAC mismatch (ctr N)` (у нормальному сеансі з'являтися не мусить),
`UL-AES command MAC mismatch, dropping session` (з боку емулятора).
