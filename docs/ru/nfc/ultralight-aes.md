# MIFARE Ultralight AES (MF0AES20)

**MIFARE Ultralight AES** — Ultralight со взаимной аутентификацией **AES-128** вместо пароля (NTAG21x) или 3DES
(Ultralight C). 60 страниц, три односторонних счётчика, 48-байтная ECC-подпись оригинальности, опциональный режим
**Random ID** и опциональный **secure messaging** (каждая команда и ответ защищены CMAC).

::: tip Unleashed
Поддержка Ultralight AES (чтение, атака по словарю, ручной ввод ключа, эмуляция, запись, расшифровка конфигурации,
Random ID, secure messaging) — функция Unleashed, проверенная на настоящей MF0AES20 против эталона Proxmark3.
:::

## Что умеет Флиппер

| Функция | Подробности |
|---|---|
| Определение и чтение | Определяется как `Mifare Ultralight AES`, ATQA `0044`, SAK `00`, `60/60` страниц на открытой метке, счётчики. |
| Подпись оригинальности | Сохраняется в `.nfc` строкой `AES signature:` (48 байт) и отдаётся при эмуляции — проверка подписи считывателем проходит. |
| AES-аутентификация | Трёхпроходный AES challenge-response, затем чтение защищённых страниц. |
| Атака по словарю | Сама запускается при неполном чтении: **MFUL AES User Dictionary**, затем **MFUL AES System Dictionary**. |
| Ручной ключ | `Saved → <метка> → Unlock` → **«Enter key in hex»** (16 байт) → подтвердить **Unlock**. |
| Управление ключами | `NFC → Extra Actions → MIFARE UL AES Keys` → **Add** / **List**. |
| Запись | **Write (Keep Key)** / **Write (Copy Key)** для полностью прочитанного дампа. |
| Эмуляция | Полная, включая AES-аутентификацию как метка, проверку AUTH0 и secure messaging. |
| Расшифровка конфига | В `Info` — блок **UL-AES Config** (см. ниже). |
| Random ID | Определяется и показывается (`Random ID: on`); **Reveal Real UID** пытается достать настоящий UID. |

Словари: системный `/ext/nfc/assets/mf_ultralight_aes_dict.nfc` (заводской нулевой ключ, `BREAKMEIFYOUCAN!` как AES и
другие распространённые значения из Proxmark3), пользовательский `/ext/nfc/assets/mf_ultralight_aes_dict_user.nfc`.
Заводская метка использует нулевой ключ `00000000000000000000000000000000` и для DataProtKey, и для UIDRetrKey.

## Чтение защищённой метки

1. `Main Menu → NFC → Read`, приложите метку.
2. Открытые страницы читаются; если у метки есть область под AES, атака по словарю запускается сама (сначала
   пользовательский словарь, потом системный).
3. Если ключ подошёл, читаются все страницы, ключ показывается и сохраняется вместе с дампом. Если нет — частичное
   чтение (например, `42/60` страниц) и **«AES-protected pages!»**, без зависаний и без расхода попыток на метке без
   лимита.
4. Сохраните метку. Позже можно повторить **Unlock with Dictionary** (после добавления ключей) или **Unlock**
   (ручной ключ).

::: warning Порядок байтов ключа
Прямая запись страниц (например, `hf mfu wrbl` в Proxmark3) хранит ключ в **порядке памяти метки**; AES-движок,
ручной ввод на Флиппере и `hf mfu aesauth --key` в PM3 используют **обратный** порядок. Метка, у которой страницы
`0x30–0x33` читаются как `A0A1A2A3 A4A5A6A7 A8A9AAAB ACADAEAF`, аутентифицируется ключом
`AFAEADACABAAA9A8A7A6A5A4A3A2A1A0`. Вводите вручную восстановленный ключ **в AES-порядке**. В сохранённом `.nfc`
страницы ключа (`Page 48`–`51`) хранятся в порядке памяти метки, чтобы их можно было записать обратно как есть;
строка `DataProtKey:` на экране — только отображение.
:::

## Память и конфигурация

| Что | Где |
|---|---|
| DataProtKey | страницы `0x30`–`0x33` |
| UIDRetrKey | страницы `0x34`–`0x37` |
| CFG | страница `0x29`: байт 0 бит0 = `RID_ACT`, бит1 = `SEC_MSG_ACT`; байт 3 = `AUTH0` |
| ACCESS | страница `0x2A`: байт 0 бит2 = `CNT_RD_EN`, бит3 = `CNT_INC_EN`, бит6 = `CFGLCK`, бит7 = `PROT`; байты 2–3 = `AUTH_LIM` |
| LOCK_KEYS | страница `0x2D`: байт 0 = биты блокировки ключей |

Блок **UL-AES Config** в `Info` расшифровывает их, например:

- `Auth from: off (open)` или `Auth from: page 0x10 (r+w)` / `(write)` — `AUTH0` и `PROT`;
- `Auth limit: unlimited` или `Auth limit: N (locks!)`;
- `Counter 2: rd open / inc auth` и т.п.;
- `Random ID: on/off`, `Secure msg: on/off`, `User cfg: open/locked`, `Key lock: DP N / UID N`;
- `Real UID:` — когда настоящий UID раскрыт.

::: danger Не экспериментируйте с этими битами
`CFGLCK` блокирует конфигурацию **навсегда**, `AUTH_LIM` включает блокировку после неудачных аутентификаций, а
`LOCK_KEYS` и статические lock-байты могут «закирпичить» метку. Не трогайте их на нужной метке. Учтите также, что
`hf mfu info` в PM3 подписывает страницы `0x34`–`0x37` MF0AES20 по старому шаблону Ultralight (`cfg0/cfg1/PWD/PACK`) —
верьте таблице выше.
:::

## Запись дампа

Доступна только для **полностью прочитанного** дампа Ultralight AES, двумя пунктами:

- **Write (Keep Key)** — пишет страницы данных `0x04`–`0x27`; ключ целевой метки остаётся.
- **Write (Copy Key)** — страницы данных плюс **DataProtKey** (`0x30`–`0x33`) из дампа.

Правила, зашитые в прошивку:

- Запись **сначала аутентифицируется к целевой метке** ключом из словаря — значит, *текущий* ключ целевой метки должен
  быть в словаре (заводской нулевой там есть).
- Страницы конфигурации/блокировок `0x28`–`0x2F` **никогда** не пишутся; UIDRetrKey (`0x34`–`0x37`) тоже никогда.
- Целевая метка должна быть того же **типа**; UID может не совпадать.

## Эмуляция

`Saved → <метка> → Emulate`. Эмулированная метка отвечает на GET_VERSION, отдаёт подпись, счётчики и конфиг как
настоящая, проходит AES-аутентификацию как метка с ключом `reverse(страницы 0x30–0x33)`, отклоняет неверные ключи и
соблюдает `AUTH0`. Нюанс: чтение закрытой области без аутентификации возвращает «прокрученные» данные начальных
страниц, а не NAK.

## Random ID

При включённом `RID_ACT` метка при каждом выборе отдаёт **случайный 4-байтный UID, начинающийся с `08`**; настоящий
7-байтный UID скрыт до аутентифицированного чтения. Флиппер показывает случайный UID и `Random ID: on`. Для таких меток
в меню есть **Reveal Real UID**: после предупреждения метка перечитывается с попыткой аутентификации (нулевой
UIDRetrKey по умолчанию), и статический UID показывается как `Real UID:` в конфиге.

## Secure messaging (CMAC)

При включённом `SEC_MSG_ACT` после аутентификации **каждая** команда и ответ должны нести CMAC. Флиппер работает
адаптивно: после аутентификации первый обычный `READ`/`WRITE` не проходит (настоящий чип просто молчит — считыватель
видит таймаут), прошивка повторяет аутентификацию и переключается на `READ`, `READ_CNT` и `WRITE` с MAC. Счётчик
команд растёт на 2 за обмен (команда — `CmdCtr`, ответ — `CmdCtr+1`). Проверено на железе: полное чтение 60/60 по CMAC
без единого несовпадения MAC, счётчики по CMAC, страницы ключей `0x30`–`0x37` в дампе замаскированы нулями, запись
страниц данных по CMAC.

Эмулятор тоже умеет secure messaging: проверяет MAC команды, оборачивает каждый ответ, заменяет ACK на `WRITE`
отдельным MAC и рвёт сессию при неверном MAC.

::: warning Возможность отката
После включения `SEC_MSG_ACT` запись конфига в защищённой области требует записи с CMAC, которую Proxmark3 не умеет, а
Write Флиппера пропускает (страницы конфига не пишутся никогда). Не ставьте `AUTH0 ≤ 0x29` на метке с secure
messaging, иначе можете не суметь его выключить.
:::

### Отладочные сообщения

С `Settings → System → Log Level → Debug` в логе видно, что происходит, например
`UL-AES: plain read failed post-auth, switching to secure messaging`, `UL-AES response MAC mismatch (ctr N)` (в
нормальной работе появляться не должно), `UL-AES command MAC mismatch, dropping session` (на стороне эмулятора).
